Estate Genome · the birth check

Every part is born knowing what it is, how to prove it, how to be removed, and where to stop.

Estate Genome is a check that every piece of software must pass before it is trusted: a code repository, an AI agent, a contract, a model or a service. It is admitted as a cell only when four things hold, and the check proves them by running the part's own code: it describes itself; its judge tells right from wrong; it reports its health and can be removed and put back exactly; and it refuses work outside its lane, naming who that work goes to. A part that fails any one is not admitted, and the check says exactly why.

… admitted cells in … live public repositories mutation gate …/… clean census checked …, every day on GitHub's servers MIT licence · runs on your own machines

1Describe

It ships a seed.json: what it is, what it takes, what it refuses, how to check it, where it came from. Any person or AI agent can find it and know how to use it without asking anyone.

2Verify

It names its judge, the check that makes its output right. The birth check gives the judge a known-good case and a known-bad case. A judge that calls the bad case "verified" fails.

3Prune

It reports its health, and it can be retired reversibly. The birth check retires a copy of it, then restores it, and the result must match the original byte for byte.

4Boundary

It declares its lane. The birth check hands it one input inside the lane, which it must accept, and one outside, which it must refuse, naming who to escalate to.

Start here

  1. Check a manifest in this tab. In Try it, pick an example or paste your own seed.json. The page runs the same check code the command line runs, and lists what is missing.
  2. See the four traits proved on real runs. Further down, open DocDec, the honest example or the bluffing example. You will see each hook's actual output from a real run, judged again in this tab.
  3. Run the full birth check on any folder. You need Node.js 20 or newer. 
    git clone https://github.com/sjgant80-hub/estate-genome
node estate-genome/bin/genome-check.mjs path/to/your/part
    It prints one line per trait and exits 0 only for a cell.
  4. Give your own repository the genome. grow plants seed.json, the genome/ hooks and the CI workflow, and never overwrites anything: 
    node estate-genome/bin/grow.mjs path/to/your/repo --name my-part --purpose "What it does, in a sentence." \
  --lane my-lane --accepts "what it takes" --refuses "what it turns away" --in "input" --out "output" \
  --judge-what "what makes an output right" --escalate my-team --repo my-org/my-repo --by "My team"
    A freshly grown part is honestly not admitted. It names the three things only you can write: the judge, the lane check, and a good and a bad case. Write them in genome/cell.mjs and seed.json, and it becomes a cell.
  5. Make the check run in CI. The planted workflow runs it on every push: 
    - uses: sjgant80-hub/estate-genome@v1
  6. Route work by the genome. In the conductor box, type what you need. Only admitted cells can receive work, and a request no cell's lane fits is refused and escalated.

How it works

The birth check reads the part's seed.json, then runs the part's own hooks, each as a command with a time limit: the judge twice, the lane check twice, the health report once, and the retire-and-restore on a scratch copy. It hands what the hooks printed to a small kernel that judges each trait. This diagram is DocDec's real run, from the trace above.

  1. Describe. The kernel reads the manifest and makes … checks that it is complete and well-formed: the genome version, a name, a kind, a purpose, the lane and what it takes and refuses, the input and output, the judge, a good and a bad case that differ, two lane samples that differ, who to escalate to, the hook commands, and the repository, maker and date it came from.
  2. Verify. The judge runs on the good case and must answer verified, exiting cleanly. It runs on the bad case and must not answer verified. Every answer is one of three words: verified, unverified or refused. A judge that cannot tell the two apart is a rubber stamp, and the bluffing example shows one being caught.
  3. Prune. The health hook must report whether the part's own judge still passes (measured, true or false), and what it knows about its use (true, false, or null for not measured, said honestly). Then the part is copied to a scratch folder. Its retire command runs there and must change it; its restore command must bring back a byte-identical copy.
  4. Boundary. The lane check runs on the in-lane sample, which it must accept. It then runs on the out-of-lane sample, which it must refuse, escalating to exactly the party the manifest names.
  5. Verdict. All four hold: a cell. In CI that is a green check; the daily census lists it; the conductor can route to it. Anything else is a part, with the failures named in words a person can act on.

Security, data protection and compliance, answered straight

QuestionAnswer
Does the birth check run our code?Yes. It runs the part's own hooks, the way CI runs its tests. Run it where you would run that part's tests.
Can a hook hang, or leave processes behind?Each hook has a time limit (60 seconds by default). It runs under a supervisor that kills the hook's whole process tree when the limit is hit. A test proves the tree is gone, on Linux and Windows.
Does retiring touch the real part?No. Retire and restore are tried on a scratch copy in the system's temporary folder, and the check only ever deletes folders it made itself.
What leaves our machines?Nothing, for the birth check and grow. The census and the conductor read GitHub (the public interface in the daily census). There is no telemetry.
Can a part fake a pass?It can write anything in its manifest, but the check runs its judge on its own bad case. A judge that says "verified" to everything fails, as the bluffing example shows. A weak judge that separates its one bad case from its one good case can still pass. The check proves the judge is not a rubber stamp, not that it is complete.
Is there an audit trail?Yes. genome-check --json writes a report of every hook's input, output and exit code, and the verdict for each trait. In CI the run log keeps the per-trait lines for every push. The daily census commits its results, so the repository's history records every day's verdicts.
What do we install?Node.js, and this repository. It has no dependencies, and nothing is installed on the part. The Action is tagged v1; pin a commit instead if your policy requires.
What happens when a hook fails?A hook that crashes, times out or prints nothing fails its trait, and the report says which and why. Nothing else is touched, and the part is simply not admitted.
Does it make us compliant?No tool does that on its own. For each part it gives you a written purpose, a stated lane, a named judge with a test, a named escalation and a reversible removal. AI governance and change control ask for those records. It certifies nothing.
Personal data?The genome holds descriptions of software, not personal data. The census publishes repository names and lanes for public repositories only.

Rolling it out

  1. One repository first. Run grow on a part you know well, write its judge, lane check and cases, and turn on the Action.
  2. New parts are born with it. Put the workflow in your repository template, so every new part starts as an honest "part" that names what it still needs.
  3. Count. Run the census over your organisation to see how many parts are cells, declared, or genome-less.
  4. Let the metabolism work. Upgrade the genome-less parts that are in use, and retire the measured-dead ones, reversibly, with a person's sign-off.
  5. Route by lane. Send work, including your AI agents' work, only to admitted cells whose lane takes it. Escalate the rest to a named owner.

White paper: four instructions, and why only four

The problem. This estate's own first full scan found … live repositories: … had no measured signal saying they were healthy or broken, and … were measured unused and broken, unverified or superseded (the estate metabolism). Nobody built them to be unknowable. They were built with no way to say what they are, prove it, be removed, or stay in their lane, so finding out cost a person a hunt every time.

The idea. Give every part the same four instructions at birth, and refuse the part until it obeys them. Each instruction is load-bearing, and dropping one has a named failure:

  • Without describe, a part is invisible. Nothing can find it, route to it or combine it with anything without a person explaining it.
  • Without verify, a part can hand out wrong output as right, and everything that uses it inherits the error.
  • Without prune, the estate only grows. Nothing can be removed safely, so it all stays.
  • Without boundary, a part bluffs past its competence, and combining parts stops being safe.

What is not new, and what is. Describing software is old: package manifests, service catalogues such as Backstage's catalog-info.yaml, and API descriptions all do it. Health checks are old too (Kubernetes probes, for example). What the genome adds is that the birth check runs the claims. It feeds the judge a known-bad case, retires and restores a copy byte for byte, and probes the lane from both sides. A manifest on its own cannot pass.

Why only four. Every instruction in the genome is inherited by every part, for good. So the bar for a fifth is high: it would have to name a failure these four cannot catch. A small genome is what lets it fit everywhere.

How it spreads. New parts are grown from the template, so they carry all four from the first commit. Old parts are not rewritten in one go. The metabolism flags the genome-less ones; the ones in use are upgraded, and the dead ones are retired reversibly. The census counts the result every day.

Limits, stated plainly

  • It makes parts self-checking. It does not make them intelligent or aware, and it does not claim to.
  • A passing judge separates its own good and bad cases. It is not proof that the judge catches every wrong output.
  • Health values can be null. A part that cannot measure its own use says so, rather than guessing.
  • The browser check on this page covers the manifest (trait 1). The other three need the part's code, and run on the command line and in CI.
  • The conductor ranks by the words in each manifest. The command-line conductor then confirms with the cell's own lane check before handing over work. It does not understand requests.
  • The public census covers public repositories only. Today … are cells. The rest have no genome yet.
  • No outside organisation has deployed it yet. The three cells are this estate's own, and the census figures are this estate's.
  • Three repositories are fitted so far: estate-genome itself, DocDec, and one private service. All three use Node.js hooks; the runner takes any command.
